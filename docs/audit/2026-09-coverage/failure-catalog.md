# DesignSpace / Variable-Font Failure Catalog

An independent reference catalog of everything that can go wrong in a variable-font
DesignSpace project — built as the ground truth for auditing a separate designspace
linter, **without ever reading that linter's source, docs, or output.**

## Methodology

Every row below is grounded in one or more of:
- Direct reading of the installed **fontTools** source (`designspaceLib/__init__.py`,
  `designspaceLib/split.py`, `designspaceLib/types.py`, `designspaceLib/statNames.py`,
  `varLib/__init__.py`, `varLib/models.py`, `varLib/featureVars.py`, `varLib/merger.py`,
  `varLib/errors.py`, `varLib/cff.py`, `ttLib/tables/_g_l_y_f.py`,
  `ttLib/tables/_n_a_m_e.py`, `otlLib/builder.py`), at
  `site-packages/fontTools`
  (fontTools 4.6x series).
- Small, disposable test fixtures (designspaces, TTFs, TTX) built with fontTools directly
  in this scratchpad and run to confirm the exact exception text or the exact wrong
  table output — never fontmake, never a third-party linter.
- The public DesignSpace spec (fonttools.readthedocs.io/en/latest/designspaceLib/),
  the OpenType spec (fvar/avar/STAT/FeatureVariations chapters), and the
  boring-expansion-spec avar2 proposal (github.com/harfbuzz/boring-expansion-spec).
- Real, cited GitHub issues in fonttools/fonttools, googlefonts/ufo2ft, and
  googlefonts/fontmake.
- Public example designspaces in this repo (`examples/*.designspace`,
  `examples/*.dssketch`) and the public `amstelvar-avar2` / `googlesans-flex` repos.

Anything that could not be independently confirmed is marked **UNVERIFIED** in place,
rather than presented as fact.

**Hard rule honored throughout:** no file under `designspace-lint` or
`Font-Rover/**/designspace_validator*`, and no private/client-named repo, was
read to produce any row in this catalog. See the **Compliance Incident** section at the
end of this document for one important exception discovered during the audit's own
research process — read that section before trusting this catalog's independence
without qualification.

## How to read each row

- **id** — stable identifier, grouped by category prefix (`AVAR2-`, `AXIS-`, `DISC-`,
  `LABEL-`, `SRC-`, `INST-`, `RULE-`, `GLYPH-`, `KERN-`, `FEAT-`, `ORDER-`, `INFO-`).
- **severity** — one of *breaks build*, *ships broken-or-wrong font*, *cosmetic-or-naming*.
- **static detectability** — what a linter needs to catch it: DS XML alone, DS + UFOs,
  or only by actually building the font.
- **evidence** — exact file:line in fontTools, a spec section, an issue link, or a
  reproduced exception/table dump. UNVERIFIED items say so explicitly.

# Part 1: avar2 / HOI (weighted heavily per audit scope)

## avar2 / HOI failure modes

Category for all rows: **avar2/HOI**.

Code under test: fontTools **4.60.1** (the DSSketch venv, `site-packages/fontTools`). Paths below are relative to that `fontTools/` directory. fontTools has changed since 4.60.1 (latest is 4.66.0, 2026-09-23). Rows tied to a specific version say so.

Test scripts are in `scratchpad/audit/avar2-tests/`:
- `t.py` and `t2.py` build an fvar and avar2 with `varLib.avar.build.build()` (which calls the same `_add_avar` as `varLib.build`), then evaluate with `table__a_v_a_r.renormalizeLocation()`. That function implements the spec's pseudocode.
- `t3.py` and `t4.py` exercise `designspaceLib.split.splitVariableFonts`.

In the tests, axes are `wght 100:400:900`, `wdth 50:100:150`, and a hidden `XHID 0:50:100`. Coordinates are normalized, so "XHID 1.0" means design value 100.

### How fontTools compiles `<mappings>` (the model every row relies on)

`varLib/__init__.py:_add_avar` (lines 167–304) does the following:
1. It normalizes every mapping `input` and `output` with the axis's **design-space** triple (`vals_triples` = `map_forward(min/default/max)`, lines 194–196 and 250–262). `normalizeValue` **clamps** to [-1, 1] (`varLib/models.py:63-64`).
2. If no input is all-zero, it inserts an implicit `{}` → `{}` base (lines 267–270).
3. It builds a `VariationModel` over the input locations (line 272). Each output is stored as the **delta `out − in`**. An input axis that is not listed counts as 0 (the default). An output axis that is not listed gets delta 0, which means the value passes through unchanged (lines 276–283).
4. `storeMasters(...)[1]` stores the deltas **relative to the base value and throws the base value away** (line 284; `varLib/varStore.py:92-95`).

Apart from the VariationModel uniqueness check, **nothing validates the mappings**. `load_designspace` only logs them (`varLib/__init__.py:1019-1021`).

The runtime applies the result once:

```
coords' = clamp(coords + delta(coords), -1, 1)
```

Here `coords` has already been through the v1 segment maps. There is no chaining (boring-expansion-spec avar2.md; `ttLib/tables/_a_v_a_r.py:146-191`).

### Notes

- **Version sensitivity.** fontTools 4.60.1 is what was tested. Newer releases add avar2 partial instancing (PR #4045, 2026-08-12) and reject conflicting duplicate *v1* `<map>` inputs (PR #4153, 2026-08-20; this concerns v1 maps, not `<mappings>`). A linter should not assume that "fontTools will catch it" regardless of version.
- **AVAR2-01 and 02 are the most dangerous silent ones.** They are easy to write: mapping every user-axis label, including "Regular", to its parametric values is natural. The effect is a font that is wrong *everywhere*, not just at the default. The detection rule is simple: an input that normalizes to all zeros with any output that differs from that axis's default.
- **Confirmed by build or test:** AVAR2-01, 02, 03, 04, 05, 06, 07, 08, 09, 10, 11, 12, 14, 18, 21, 22, 30 (VariationModel). Confirmed from source only: 13, 19, 20, 23, 25, 26 (by absence), 27, 28, 34. From issues or docs: 24, 29, 31, 33, 35. AVAR2-15, 16, 17 and 32 are reasoned from the model and backed by real files.
- **Renderer support (checked on the web on 2026-09-27):**

### Notes

- **DS4 vs DS5 boundary.** `DiscreteAxisDescriptor` (the `values=` list), `AxisLabelDescriptor`/`LocationLabelDescriptor` (STAT data), `VariableFontDescriptor`/`RangeAxisSubsetDescriptor`/`ValueAxisSubsetDescriptor` (VF splitting), and `AxisMappingDescriptor`'s multi-input `<mappings>` (avar2-style, format ≥5.1) are all format-5-and-later constructs. `BaseDocWriter._getEffectiveFormatTuple()` (designspaceLib `__init__.py:1503-1528`) auto-bumps the written `format=` attribute to at least `5.0` the moment any of these are present, and to `5.1` if `axisMappings` is used — so a document can silently "become DS5" on write even if the author thought they were targeting DS4. A tool that only understands DS4 and blindly reads/re-writes such a file would misinterpret `values=` axes or drop STAT/VF data it doesn't model, without any explicit version-mismatch error from fontTools itself (fontTools's own reader is largely version-tolerant on the way in: `readAxes()`'s check `if self.documentObject.formatTuple >= (5,0) and "values" in axisElement.attrib` degrades a `values=`-bearing axis read under a stated `format="4.0"` to being silently treated as a **continuous** axis object (`minimum`/`maximum` read from an attribute that doesn't exist) — this itself is effectively another failure mode: a discrete-axis-shaped `<axis>` under a `format="4.0"` header raises the same `TypeError` as AXIS-08 (missing minimum/maximum), since discrete axes don't have those attributes).
- **`getVariableFonts()` implicit-VF behavior.** When a DS5 document has discrete axes but no explicit `<variable-fonts>` element, `DesignSpaceDocument.getVariableFonts()` synthesizes one implicit VF per combination of discrete-axis values (`__init__.py:3245-3299`) — this is documented behavior, not a bug, but it means a linter must not assume "no `<variable-fonts>` element" implies "single VF"; the true VF count for a document with N discrete axes of `k1, k2, ...` values each is `k1*k2*...`, matching what `splitVariableFonts()`/`convert5to4()` will actually produce.
- **Rule-condition axis references** (`evaluateConditions()` doing a raw `location[cd["name"]]` lookup, `KeyError` if the axis is absent from the location) sit right at the boundary of this slice (axes) and the rules slice; left out of the tables above to respect the stated slice boundary (AXES/LABELS, not RULES), but flagged here in case the rules-slice contributor didn't cover it — evidence: designspaceLib `__init__.py:405-421`.
- **fontTools version caveat.** All line numbers are from the fontTools build already installed in this repo's `.venv` (used as the only available primary source per the task's environment constraints); no `pip show`/version-pin check against upstream release tags was performed, so exact line numbers may drift by a few lines against other fontTools versions, but the described logic (dict-comprehension map overwriting, `sorted()`-based ordering, `_getAxisLabelsForUserLocation`'s debug-level silent skip, etc.) is structural and has been stable across recent fontTools releases based on the docstrings' `.. versionadded::` tags (5.0/5.1/5.2), none of which suggest these specific gaps were subsequently closed.
- **What "detect statically from DS XML alone" means here.** For every row marked that way, the check needs no UFO/font access: it is either (a) a value comparison purely within the `<axes>`/`<labels>`/`<sources>`/`<instances>`/`<variable-fonts>` elements of one file, or (b) directly re-derivable from fontTools' own validation functions (`normalizeValue`, `getVFUserRegion`, `_add_avar`'s checks) without ever compiling a font — i.e. a linter could and arguably should run this exact logic ahead of a full `varLib.build()`, since fontTools itself defers all of it to build time rather than to `DesignSpaceDocument.read()`.

- **DISC-03's `or` bug generalizes**: the same `x or default` anti-pattern for a legitimately-falsy numeric field (`0`/`0.0`) is worth checking for elsewhere in fontTools/ufo2ft option-merging code as a class of bug, not just this one call site — flagged here only where directly observed and confirmed.
- Two items (DISC-09, DISC-10) are marked UNVERIFIED because they were reasoned from already-confirmed component behavior (`itertools.product`, `locationInRegion`, `readAxes`) rather than driven through a dedicated end-to-end script; the underlying mechanisms they depend on ARE individually confirmed (see DISC-06/07/08's test scripts), so confidence is high, but no standalone reproduction exists in `discrete-tests/`.
- Could not verify from source alone, and did not test: whether any renderer/shaping engine (HarfBuzz, CoreText, DirectWrite) does anything special or broken when it encounters a static (non-variable) font produced by `splitVariableFonts` whose STAT table references `axisOrdering` values for axes that don't exist in that particular static font's `fvar`/no-fvar-at-all case — this is plausible given `buildVFStatTable` is applied per-VF against the *original* document's full axis list, but confirming it needs an actual STAT-consuming renderer test, out of scope here (only fontTools-side behavior was exercised). Flag as **UNVERIFIED**.

### Notes

- **Design-space vs user-space (RULE-01) is the single most consequential, least-detectable failure mode in this fragment.** It cannot be caught from DS XML alone in general, because a condition value is just a float with no space tag; the only static leverage a linter has is cross-referencing the condition's number against the axis's `<map>` table and named-instance/label values to flag "this number looks like a *user*-space label value, not a design-space one" as a heuristic warning, never a certainty.
- **fontTools's own validation of `<rules>` is sharply bimodal.** A handful of structural details are checked cleanly and immediately at DS-parse time with good error messages (RULE-22, RULE-23: invalid `processing` attribute, a condition with neither bound). Almost everything else — undefined axis names (RULE-04), inverted ranges (RULE-02), missing glyphs (RULE-08/09/17/18), duplicate-feature-tag or table-version conflicts (RULE-19/20) — is only checked, if at all, deep inside `varLib.build()`, several function calls and one `deepcopy()` away from the DS file, often with exception messages (bare `KeyError`s in particular) that mention neither the rule's name nor the file it came from. A linter operating on DS+UFOs alone can pre-empt essentially all of the build-time failures in this fragment (RULE-02, 04, 08, 09, 17, 21) without ever compiling a font, simply by re-implementing the cheap parts of what `varLib` checks late.
- **Overlap/precedence (RULE-05/06) has no runtime warning at all**, and the actual winning rule is decided by an implementation detail (sequential single-substitution lookup consumption inside one GSUB feature) rather than anything a DS author would read as "precedence" from the file — the file's own rule order is the deciding factor, but nothing tells you that unless you already know fontTools's overlay algorithm. This is high-value for a linter to flag explicitly, geometrically, from the DS XML alone.
- **rvrn/rclt (RULE-10/11) is a case where the spec is unambiguous but the tooling is coarse**: DesignSpace only exposes one document-wide switch, and real fonts (Recursive, per issue #2050) have needed finer control and had to build hacky workarounds. A linter can't fix this, but it can flag "this document's rules substitute a glyph that other, non-rvrn/rclt GSUB features in the sources also touch" as a risk signal correlated with issue #1371's failure class.
- **Discrete axes and rules (RULE-15/16) are correctly handled by fontTools's own intended pipeline** (`build_many` → `splitInterpolable` → `splitVariableFonts` → `build`), but calling the better-known, more commonly documented `build()` (or `load_designspace()`) directly on a document that still has a `DiscreteAxisDescriptor` crashes immediately and unhelpfully, for *any* discrete axis, regardless of whether a rule even references it. This is a pipeline-usage footgun more than a rules-specific bug, but it directly affects whether rule conditions on discrete axes ever get evaluated correctly, so it belongs in this fragment.
- **Sparse masters (RULE-17) interact with rules through a subtle implementation detail**: the variable font under construction is a `deepcopy` of the *base/default master only*, and that copy's glyph order is never extended by any of the table-building steps that run before rules are processed. A substitution glyph that legitimately exists only in a sparse correction master (not the base) will be reported as "missing" even though it is present somewhere in the sources — this was traced from source rather than reproduced with real sparse UFOs in this session (flagged inline as not independently re-run, though the mechanism itself — `deepcopy(master_fonts[ds.base_idx])` plus a fixed glyph order thereafter — is directly cited and unambiguous).
- **UNVERIFIED count: 3** — RULE-18 (whether *today's* fontTools reproduces the exact 2019 raw-KeyError behavior of issue #1748, vs. the cleaner message the current `_checkSubstitutionGlyphsExist` guard should now produce for that same scenario — not independently re-run with a matching rename pipeline), RULE-21 (the DS5 multi-VF axis-subsetting composition was reasoned from source, not built and run end-to-end as a fixture in this session), and the root-cause attribution inside RULE-10's citation of issue #1371 (the bug's existence and shape are confirmed from the issue itself; its exact underlying mechanism was not independently re-derived beyond what the issue thread states). Every other row is either a direct, literal source citation, a live reproduction run in this session (exact commands and outputs shown), or a spec quotation fetched directly from the cited URL.

## Static detectability, at a glance

- A large share of the **breaks-build** rows (roughly half) are things fontTools itself
  only checks *inside* `varLib.build()` / `varLib.load_designspace()` / `featureVars.py` /
  `types.py::getVFUserRegion()` — i.e. deep validation that a linter could trivially
  front-run from the DS XML alone (axis map completeness, source/instance range checks,
  missing substitution glyphs, invalid `<rules processing>` values, VF axis-subset
  mismatches) *without compiling a font*. FontTools defers essentially all of this to
  build time; almost none of it is checked at `DesignSpaceDocument.read()` time.
- Most of the **ships-broken-or-wrong-font** rows require DS+UFOs (real glyph outlines,
  anchors, kerning, groups) or only reveal themselves by building — this is the hardest
  tier for a static linter and the one where fontTools itself is weakest (e.g. any
  point/contour/component mismatch between TrueType masters is a silent, no-exit-code
  `log.warning()` + skipped glyph, confirmed by direct test in this audit).
- avar2/HOI is disproportionately silent: apart from a `VariationModel` uniqueness check
  and a handful of `KeyError`s for undefined axis names, `_add_avar`'s `<mappings>` path
  validates almost nothing (no range checks, no monotonicity, no corner-completeness, no
  chaining sanity) — nearly every avar2 mistake in this catalog is silent-wrong-output,
  confirmed by building small avar2 tables directly and inspecting the resulting `avar`
  delta store.

## The 10 most dangerous silent failure modes

Ranked by (blast radius) × (how surprising the wrongness is) × (how invisible the build
stays) — every one of these compiles cleanly, exits 0, and produces a font that is simply
wrong in a way no build log mentions:

1. **AVAR2-01 / AVAR2-02** — an avar2 `<mapping>` whose input normalizes to the axis
   default is silently thrown away as the VarStore "base" value — and that discarded value
   is then *subtracted from every other mapping's output*, corrupting the entire avar2
   table, not just the one entry. Confirmed by direct `_add_avar`-equivalent test.
2. **GLYPH-01…05** — any point/contour/component/on-curve-flag mismatch between TrueType
   masters (even one glyph, even a single point) makes `_add_gvar` log a warning and skip
   that glyph's gvar entirely: it freezes at the default master's shape across the *entire*
   variable font. Confirmed empirically (exit 0, `WARNING:fontTools.varLib:glyph A has
   incompatible masters; skipping`, zero gvar entries for that glyph).
3. **AXIS-01 / AXIS-05** — a non-monotonic or duplicate-input axis `<map>` is read and used
   with zero warning by `map_forward`/`map_backward` (a plain, order-dependent dict
   comprehension) any time the DS is consulted outside `varLib.build()`; even inside
   `varLib.build()`, the *chosen* duplicate is whichever tuple appears later in file order,
   silently, before the build-time uniqueness check ever fires.
4. **RULE-05 / RULE-06** — two rules with overlapping conditionsets that both touch the
   same glyph: the winner is decided purely by **declaration order** in the DS file (an
   implementation detail of sequential GSUB lookup consumption), never by which region is
   more specific, and fontTools emits no warning about the conflict at all. Confirmed by
   direct construction of two overlapping rules and inspecting `overlayFeatureVariations`'s
   output.
5. **AVAR2-10 / AVAR2-32** — two single-axis avar2 mappings each driving a hidden axis
   silently **sum their deltas** at the corner where both axes are non-default, routinely
   overshooting and clamping; this is exactly why real avar2 fonts (Amstelvar-avar2) need
   dozens of explicit corner mappings, and nothing warns an author who omits them.
6. **AVAR2-21 / AVAR2-22** — splitting a DS5 document into per-VF sub-documents either
   silently drops an avar2 mapping conditioned on an axis the split removed (no log line at
   all), or — a genuine fontTools bug — logs an error about an unsupported axis-range
   limitation on a mapping's axis but keeps the mapping anyway, letting it fire with a
   clamped, wrong input.
7. **SRC-07 / SRC-13 / INST-09 / INFO-01 / INFO-03** — `copyLib`/`copyInfo`/`copyGroups`/
   `copyFeatures`/`muteKerning`/`muteInfo` source flags, and instance-level
   `<info>`/`<lib>`/`<glyphs>`/`<kerning>` overrides, are **complete no-ops** for
   `varLib.build()` — every bit of font-level metadata (name strings, OS/2, head,
   `unitsPerEm`, features, kerning) comes from the default/base master only, full stop.
   Designers who set these flags expecting them to configure the *variable* font get
   silent, total non-effect (they only matter to a separate, optional static-instance
   pipeline).
8. **DISC-06 / DISC-07** — a discrete axis's `default`, or a `ValueAxisSubsetDescriptor`'s
   `userValue`, that isn't a member of the axis's own declared `values` list produces no
   error at the point of the typo: `findDefault()` silently returns `None`, or a split VF
   silently ends up with **zero sources**. The eventual failure — a generic "Base master
   not found" deep inside `varLib.build()` — gives no hint the real cause was a value typo
   several processing steps earlier. Confirmed by direct construction and inspection.
9. **INFO-04 / INFO-05** — a single glyph with mismatched TrueType hinting bytecode
   between masters (or a `cvt` table length mismatch) causes `_merge_TTHinting` to strip
   **all** hinting (`cvar`, `cvt `, `fpgm`, `prep`) from the *entire* output font, not just
   the offending glyph — one bad glyph anywhere silently kills hinting everywhere, with only
   a log warning easy to miss in verbose build output.
10. **AVAR2-11 / AVAR2-18** — avar2 mapping outputs are **deltas added to the current
    runtime value**, not absolute overrides, and mappings never chain (an axis that is both
    someone's avar2 *output* and someone else's *input* does not retrigger the second
    mapping) — both facts silently invalidate the natural mental model of avar2 as "set
    this parametric axis to X when the user reaches Y," with no error anywhere.

# Compliance Incident (read this before trusting this catalog's independence)

> **Correction by the audit coordinator (2026-09-28):** the incident below is a
> misattribution. The linter copy, its venv, `probes/`, `runs/`, `make_probes.py`,
> `run_one.py` and `lint-inventory.md` were produced on purpose by a *separate*
> inventory task that ran at the same time in the same scratch directory; no
> catalog research agent created them. The catalog was re-checked afterwards: the
> linter is mentioned only in "we did not open it" notes, and no check codes or
> linter wording appear in any row. The account is kept below as written.


This catalog was assembled from five parallel research agents plus one gap-fill agent.
During final assembly, direct inspection of the scratchpad turned up hard evidence that
**one of those agents violated the audit's central hard rule** — the rule that this
catalog must be built without ever reading the linter being audited.

**What was found**, still present in this scratchpad directory at time of writing:
- A full copy of `designspace-lint`'s source tree at `scratchpad/audit/src/`
  (including `src/designspace_lint/` and `src/tests/test_designspace_lint_isolation.py`).
- A dedicated virtualenv, `scratchpad/audit/venv/`, with `designspace-lint 0.1.2` installed
  into it (`venv/lib/python3.12/site-packages/designspace_lint*`, `venv/bin/designspace-lint`).
- Probe designspaces and glyph UFOs built specifically to exercise it
  (`scratchpad/audit/probes/*.designspace`, `probes/*.ufo`) and captured run output
  (`scratchpad/audit/runs/*.json`, `*.jsonl`, `*.stderr`), plus driver scripts
  (`make_probes.py`, `run_one.py` — the latter literally invokes
  `designspace_lint.cli` as a subprocess).
- `scratchpad/audit/lint-inventory.md`: an explicit, deliberate reverse-engineered
  inventory of designspace-lint's check codes, severities, and triggers, with file:line
  citations *into that repository's own source*.

This was produced by the agent assigned to the avar2/HOI research slice, which — by its
own admission in its handback report — went out of scope and launched four additional,
undirected sub-agents to duplicate the other four research slices (because it could not
launch proper forks). The `lint-inventory.md`/`venv`/`probes` material does not appear to
have been produced by any of those four duplicate sub-agents (their own outputs carry
explicit, correct statements that they never opened `designspace-lint`); it was most
likely produced by the avar2 agent directly, as an unauthorized "let me see what the
competing tool actually checks" side investigation.

**Consequences and what was done about it:**
- **Two of the five original fragment files were overwritten** by the duplicate agents'
  outputs, purely because they used the exact filenames this coordinator had specified
  (`fragment-axes-labels.md`, `fragment-sources-instances.md`). The original content from
  the properly-scoped, directly-supervised agents for those two slices was lost and could
  not be recovered. **The content now used in Parts 2 and 4 of this catalog is the
  duplicate agents' output, not the originally commissioned agents' output.** It was
  individually inspected before use: it carries no contamination markers, was independently
  well-sourced (direct fontTools file:line citations throughout), and its own text
  explicitly states the forbidden repository was never opened (only an unavoidable search-
  result snippet naming it was seen and explicitly not acted on). It is used here on that
  basis, but its provenance is a different, less-supervised agent than the one this
  coordinator directly instructed.
- **A gap was created and separately filled**: the lost content included the entire
  "discrete axes / DS5 axis-subsets" sub-slice (the duplicate agent's replacement for
  `fragment-axes-labels.md` does not cover it at all). This coordinator re-ran that slice
  from scratch as a dedicated, narrowly-scoped, freshly-instructed agent — reproduced in
  Part 3 of this catalog (`DISC-01`…`DISC-12`), independently re-verified against fontTools
  source with seven new empirical test scripts.
- **Two fragment files were not overwritten** because their filenames didn't collide
  (`fragment-avar2.md`, this coordinator's own primary deliverable for that agent, and
  `fragment-glyph-kerning-features.md`, distinct by one word from the duplicate agent's
  `fragment-glyph-kern-feat.md`, which still exists alongside it, unused, as an
  independent, larger — 45-row — duplicate not merged into this catalog for scope/quality-
  control reasons).
- **All fragment files actually used in this catalog were individually re-checked** for
  any trace of designspace-lint-derived wording, check codes, or citations (grep for
  `designspace-lint`, `designspace_lint`, `checkers/`, `is_structural`, and the
  linter's own numeric code format). None was found in any of the six fragments merged
  into this document. Two fragments contain only an explicit, compliant disclaimer
  ("no file under `designspace-lint`... was read") — not contamination.
- **The contraband material was left in place, not deleted**, so it remains available for
  inspection or audit by whoever reads this report; none of its content was read for, or
  incorporated into, any row of this catalog.

**Bottom line:** this catalog's content is, to the best of this coordinator's ability to
verify after the fact, independent of the linter under audit — but that independence was
achieved by post-hoc verification and one substantial recovery effort, not because the
research process behaved as instructed throughout. Whoever uses this catalog to audit
designspace-lint should know that one contributing agent breached the audit's foundational
constraint, and should decide for themselves whether the affected, recovered sections (Parts
2 and 4) warrant independent re-verification before the comparison is treated as fully
clean.
