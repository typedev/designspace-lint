## 3. Catalog corrections / clarifications

- **KERN-04's UNVERIFIED tag is about a different question than lint coverage.** The catalog marks KERN-04 UNVERIFIED because `ufo2ft` wasn't installed when that fragment was written, so the *build-time* consequence of divergent `public.kern1.*` group membership couldn't be traced from source. That uncertainty stands. But whether the **linter** catches the group-membership divergence itself is a separate, now-resolved question: it does, cleanly, via 5.2. Recommend the catalog note this distinction rather than leaving KERN-04 looking unresolved for audit purposes.
- **ORDER-02's UNVERIFIED tag**, same pattern: the catalog's uncertainty is about ufo2ft's internal reconciliation behavior for divergent `public.glyphOrder`. From the *linter's* perspective this is cleanly COVERED via 9.0/9.3, confirmed by probe.
- **FEAT-01's actual trigger condition is narrower than "some but not all UFOs have a top-level block."** It requires the comparison UFOs to have *non-empty* `features.fea` in the first place — an entirely empty `features.fea` on one master does not get compared at all, so "block present in one master, file totally empty in the other" produces **no** finding, only "block present in one master, some *other* non-empty content in the other" does. This is a real, previously-undocumented nuance in lint-inventory's own 8.1 description worth flagging back to whoever maintains that document.
- **GLYPH-10's 3-master ambiguity resolves in the linter's favor, via a different code than expected.** A glyph present in the default and one interior master but missing only from the topmost extreme master is caught not by 4.13 (which needs "present in exactly one master, the default") but by **4.11 (error, `axis_span_gaps`)** — the axis-span mechanism correctly recognizes the glyph doesn't reach the full declared range and reports it as an error, which is if anything a *stronger* signal than 4.13's warn. No gap here; my preliminary uncertainty is resolved as COVERED either way.
- **ORDER-03 (glyph rename) is caught more thoroughly than the catalog implies is necessary**: three independent codes (4.13, 4.7-as-error, 9.0) all fire for a single rename, giving strong triangulated evidence rather than one ambiguous signal.

## 4. Candidate top-gap entries (for the final prioritized list)

1. **GLYPH-13† / INFO-07† (sentinel-mismatch family)** — confirmed silent by probe. A master correctly excluded from gvar (via an emptied outline, caught by 4.12) can still carry a nonsensical advance width or underline metric that ships wrong spacing/metrics with **zero** diagnostic anywhere, precisely because it hides behind a passing/warned glyph-shape check. Common in real sparse-master setups (this repo's own `@sparse` convention is exactly the pattern at risk). DS+UFOs needed; algorithm: for any glyph flagged by 4.12 (empty in a non-default master), additionally compare that master's advance width against a straight-line interpolation of the flanking masters' widths and flag if it deviates beyond a tolerance; separately, diff `postscriptUnderlineThickness/Position` across masters when non-default values are present. False-positive risk: low-moderate (arbitrary/placeholder widths on genuinely non-participating sparse masters are common and intentional in some pipelines, so this should probably be `info`/`warn`, not `error`).
2. **GLYPH-05 as the canonical "only interpolatable/build+visual-diff can catch this"** — not a linter gap so much as a hard boundary; worth stating explicitly in the report's build-time section as the strongest argument for running `varLib.interpolatable` as a complementary step, since that tool specifically does point-correspondence/rotation analysis this digest-based checker structurally cannot.
3. **FEAT-01's narrow trigger condition** — real projects very commonly have kern/mark/mkmk generated entirely by ufo2ft's writers (not hand-authored top-level blocks in `features.fea`), which 8.1 cannot see at all; the broader "differing generated feature set per master" failure (KERN-01/02/06, FEAT-01's full scope) remains build-only. Medium priority: DS+UFO can't fully solve this without re-implementing ufo2ft's kern/mark writers, which is likely not worth it — flag as a documented limitation rather than a fixable gap.
4. **KERN-02 (kern-splitter subtable-count divergence)** — real risk on any family with large kerning tables (common for CJK-adjacent or heavily-kerned Latin families), but genuinely build-only; not actionable statically without reimplementing ufo2ft's splitter heuristic. Low priority for a static linter, note as an acknowledged blind spot rather than a target.
